# 接口规范：关卡数据（游戏 ↔ 开发者工具）

> **目的**：本项目并行开发两个组件——①玩家游戏（Godot 4.7 工程，`游戏项目/千年一榫/`）②开发者工具「挖木块编辑器」（Godot 4.7 独立工程，`关卡编辑器/voxel_level_editor/`，2026-09-12 起在本工作区落地开发）。双方**各自为独立 Godot 工程、互不 import**，仅通过本规范定义的关卡数据文件通信。本规范为双方唯一契约，接口变更须经用户确认并同步更新本文件。
>
> 关联文档：见仓库根说明（README）。

---

## 1. 总原则

- 唯一数据载体：**关卡数据文件**（本规范 §2~§5 契约 JSON；编辑器与主游戏解耦、编辑器产出=五件套、不直接产出该格式；**批次 AB-1 起「编辑器关卡搭桥导入主游戏」已实施**——消费口径=五件套重组为游戏侧单 JSON，见 §8.6 更新与 §13）。
- 格式目标：**人类可读、便于调试、跨工具通用**。初步定为 **JSON**（UTF-8，无 BOM）；若后续数据体积或性能出现问题，可切换为二进制或压缩格式，**但字段结构保持不变**（字段规格是契约，载体可换）。
- 版本控制：每个数据文件带 `format_version` 字段（当前 `1`），游戏加载时校验；不兼容则拒绝加载并提示。
- 一个关卡 = 一个 JSON 文件；文件命名：`level_chapter{章节号}_{关卡名}.json`，例如 `level_chapter2_baoguosi.json`。
- **游戏侧必须容错**：任何字段缺失/越界，游戏给出明确错误提示而非崩溃（见 §5 校验表）。

## 2. 顶层结构

```json
{
  "format_version": 1,
  "level_id": "chapter2_baoguosi",
  "chapter": 2,
  "title": "保国寺瓜棱柱斗拱",
  "era": "宋",
  "theme": "bud/stone",                   // 备用：主题标识（默认木纹）
  "description": "难求…",                // 关卡描述（展示用，可选）
  "anim_time": 100,
  "grid_size_unused": 0,
  "pieces": [
    "pieces" 数组：本关需要依次完成的对接步骤（每项含三件套数据），见 §3
  ]
}
```

> 说明：`title/era/description` 供章节选择与读档界面展示；`chapter` 决定章节序号与解锁依赖。

## 3. `pieces` 数组（核心：拼接步骤）

**第 1 关 = 1 个 piece；后续关 = 1~3 个 piece**（开发者按需设计，游戏按顺序逐个完成，做完一个 piece 才出现下一个）。

每个 piece 的结构：

```json
{
  "piece_id": "p1",
  "name": "月梁上方榫头",
  "block_size": { "x": 12, "y": 4, "z": 6 },     // 玩家初始组合体尺寸（体素数），由开发者工具自定义，例如 16×3×8
  "target_size": { "x": 12, "y": 4, "z": 6 },    // （批次 V 新增·可选）标准答案独立尺寸域；缺省=整缺回落 block_size
  "initial_voxels": true/false,                    // 编辑器提示字段（预留；游戏侧当前不消费）——blocks 仍必须写入全量体素列表，不可因 true 留空（见 §4 示例注）
  "blocks": [ "体素数组，见下方格式 A" ],
  "target_shapes": [                               // 玩家挖除后的期望形状（判定依据；批次 N 起按 48 变换全等价匹配——平移归一后 24 旋转+24 镜像任一命中即 success，见 scripts/join_transform.gd）
    "格式 A 数组（挖除后保留的体素集合）"
  ],
  "join_part": {                                   // 右上固定件（需要对接的木块）
    "size": { "x": 6, "y": 4, "z": 6 },
    "voxels": ["格式 A"]
  },
  "final_answer": {                                // 最终答案木块（左上面板「最终成品」渲染域：对接成功后的完整形态，仅供参照不参与判定——批次 Z Z1）
    "size": { "x": 12, "y": 4, "z": 6 },
    "voxels": ["格式 A"]                           // 语义上为「目标成品」；批次 Z Z2 起按**原样导入**口径，实测可 ≠ target∪join（第 1 关 330 vs 243，用户拍板合法态）
  },
  "match_offset": { "x": 0, "y": 0, "z": 0 }       // 可对接时的相对位姿（默认对齐原点，预留）
}
```

> **批次 V（2026-09-19）四域独立尺寸语义**（format_version 维持 1——target_size 为可选新增字段，向后兼容；v2 不启用，变更以 §12 记录形式落档）：
> piece 四域各自持尺寸——blocks↔`block_size`、target_shapes↔`target_size`（新增·可选，缺失整缺回落 block_size、缺轴逐轴回落）、join_part↔`join_part.size`、final_answer↔`final_answer.size`（join/final 的 size 原为冗余字段，批次 V 起升格为**有效消费字段**——各域体素按各自 size 裁剪，缺失同样逐轴回落 block_size）。
> 各域体素坐标界内判定=「0 ≤ c < 所属域尺寸对应维」（见 §5 校验表）；主游戏三视图渲染各按各域尺寸（level_scene `_build_views`：主视口=block_size、左上「最终成品」对照面板=final_answer.size 回落〔对照面板渲染 `final_answer` 域——批次 Z Z1 起；`target_shapes`/`target_size` 仅对接判定与锐眼差集消费、不进渲染〕、对接固定件=join_part.size 回落）。
> **兼容红线**：旧格式档（无 target_size、join/final size 缺省）全链行为与批次 V 前逐字节等价（回落即 block_size，全量回归+改前/改后 validate_level 结果 diff=0 行实证）。

### 格式 A：体素编码（voxel 数组）

```json
// 紧凑格式：相对体素坐标列表（相对木块整体包围盒原点）
// 坐标序：行优先 x 递增，再 y 递增，再 z 递增（与 Godot 世界坐标 xyz 一致）
[ "1,1,1", "2,1,1", "3,1,1", ... ]
```

**编码约定**：
- 坐标均为整数，范围 `0 <= c < block_size`；超出范围视为非法数据（见 §5）。
- 推荐配套使用 `.min` / `.max` 便于编辑器校验；游戏只消费坐标列表。
- 备选：若未来关卡体素量巨大（>万级），允许改为 RLE/位图编码，字段名 `voxels_compressed`，版本号 +1；**规范默认用坐标列表**。

## 5. 数据校验表（游戏侧加载校验，批次 V 起按域口径）

| 字段 | 规则 | 违反处理 |
|---|---|---|
| format_version | 必须 = 1 | 提示"关卡文件版本不兼容" |
| chapter | 1~5 整数 | 按 1 处理并警告 |
| pieces 非空 | ≥1 | 拒绝加载，提示数据缺失 |
| block_size（blocks 域） | 每维 1~32（体素数） | 拒绝加载并提示「体素尺寸越界」 |
| target_size（target 域，可选） | 缺省=整缺回落 block_size；已有则每维 1~32 | 拒绝加载并提示「体素尺寸越界（target_size 域）」 |
| join_part.size（join 域，可选） | 缺轴逐轴回落 block_size；已有轴每维 1~32 | 拒绝加载并提示「体素尺寸越界（join_part.size 域）」 |
| final_answer.size（final 域，可选） | 缺轴逐轴回落 block_size；已有轴每维 1~32 | 拒绝加载并提示「体素尺寸越界（final_answer.size 域）」 |
| 体素坐标 | 0 ≤ c < **所属域尺寸**对应维（blocks=block_size、target=target_size、join=join_part.size、final=final_answer.size；缺省逐轴回落 block_size） | 跳过非法体素并警告 |
| target_shapes 与 join_part.voxels | 非空 | 拒绝加载 |
| final_answer | 非空；语义上 = target ∪ join 的合成（**供校验，不强制**——批次 Z Z2 起第 1 关实测 330≠243 属用户拍板合法态，游戏测试断言=「非空 + 尺寸合法」，不再断言 union） | 空 / 坐标过滤后空集 → 拒绝加载 |

> 开发者工具**产档前自校验**（批次 W N16 去导出化后「产档」=编辑器 levels/ 槽位五件套实时自动保存，见 §8.6）：体素数量、各域界内（按各自域尺寸）、拼合正确；游戏加载时再校验一次（双保险）。
> 批次 V 兼容口径：无 target_size/size 键的旧格式档回落 block_size，零新增校验零拒载（旧行为逐字节等价，tests/test_v_level_library_domains.gd P6+探针 diff=0 行锁定）。

| 体素坐标越界（不满足 `0 ≤ c < 所属域尺寸` 对应维——blocks=block_size、target=target_size 回落、join=join_part.size 回落、final=final_answer.size 回落，批次 V 按域口径） | 该体素跳过 | level_library.gd:368、385、394（按域过滤）、:445（警告） |

> ⚠ **警告不外显**：净化警告写入 `validate_level` 返回值的 `warnings` 数组，运行时无任何消费方（不打印、不上屏）。净化是兜底不是提示通道——**工具产档前必须完成自校验**（§5 末「双保险」条目）。
> 其他：JSON 解析失败 / 顶层非对象 → 该文件计 failed（`_read_json`，level_library.gd:179-187）；目录内子目录与非 `.json` 文件忽略（level_library.gd:45）。

## 13. 玩家自定义关卡（批次 AB-4「搭桥」，2026-09-26）

### 13.1 定位与本期边界（拍板口径）

用户原话：「关于玩家自定义关卡这个，就是先做好搭桥，方便回头就是添加这功能。因为这个项目有 deadline，就在 30 号，时间有点紧。如果时间来得及，我们会考虑把自定义关卡这个功能直接加入这个游戏中。但现在的话就先不加，但是先提前做好准备。」
主会话拍板：**实现扫描载入路径，但不加任何玩家可见入口**。

本期交付（`游戏项目/千年一榫/autoload/level_library.gd` AB-4 改动）：

- **目录口径变更**（§6：`res://levels_data/user_levels` → `user://user_levels`，理由见 §13.2）；
- **扫描/校验/合并/隔离/来源标记**全链（§13.3~§13.5）；
- **载入 API + 预留 UI 挂点**（§13.6，全部以注释标注「预留 UI 挂点」）；
- **可选推荐项**：编辑器五件套 → 游戏侧契约单 JSON 转换函数 `convert_editor_level`（逻辑同 AB-1 导入脚本，§13.4）；
- **明确不做**：不加任何可见入口、不改图鉴/主菜单可见行为、不自动路由用户关卡；`scan_directory()`（启动扫描）与 `get_level(chapter)` 主进度链行为与改动前**逐字节一致**（反向护栏 R 组断言锁定：用户目录为空时内置关卡数/顺序/内容零变化）。

### 13.2 目录约定与打包可写性分析

- **现口径**：`user://user_levels/`（`level_library.gd:14` `USER_LEVEL_DIR`）。旧口径 `res://levels_data/user_levels` 以 `USER_LEVEL_DIR_LEGACY`（:16）留档、零代码消费。
- **为什么不能用 `res://`**：`res://` 在**导出打包态是只读 PCK**（export_presets.cfg 的 include/exclude_filter 只决定哪些文件进包，运行期不可向工程目录写文件）；玩家自制关卡要能落盘，**必须**用运行期可写区 `user://`（Windows 实体路径 `%APPDATA%/Godot/app_userdata/千年一榫/`）。
- **与既有约定/存档的关系**：`user://` 与游戏存档 `user://save.json` 同根同机制，**导出预设无需任何追加**（user:// 路径本就不进包；include_filter 只排除 *.md/*.gd 等源文件）。旧「项目内 `levels_data/user_levels/`」约定从未落地、零消费方，AB-4 起作废。
- **目录生命周期**：扫描路径 `scan_user_directory`/`scan_all` **只读、不擅自建目录**（玩家未造关=正常态，目录不存在时静默返回）；只有显式写盘 `write_user_level` 才 `make_dir_recursive_absolute` 建目录。
- **用户档命名**：`<dir>/<level_id>.json`（与内置 `level_chapter{N}_{名}.json` 区分，靠目录而非文件名约定）。

### 13.3 格式契约与校验容错纪律

- **格式契约零差异**：用户关=§2~§5 同一契约（`format_version=1` 全套键），过**同一个** `validate_level`（:293）。
- **双来源标记**：条目级 `source: "builtin" | "user"`（AB-4 新增，内置表在 `_scan_builtin_dir` 打 `builtin`；用户表打 `user`）+ 既有 `is_user_created: true`（条目级与 `data` 体内同时置位，向后兼容旧口径）。
- **坏档逐文件隔离**（与内置扫描 W9-2 纪律**完全一致**，见 `scan_user_directory_ret`，:115-167）：单坏档只影响自身——跳过 + `push_warning` 告警 + `_user_errors[level_id]` 按 id 留痕（缺 id 回落文件名）+ `failed` 计数；**不影响其余用户档、更不触碰内置表/`_errors`**；`scan_finished` 恒发（`scan_all` 恰发一次，loaded/failed 为两表合计）。
- **坏档分表**：`_user_errors`（用户域）与 `_errors`（内置进度域，`get_error(chapter)` 既有语义）严格分表，不混用。
- **写盘纪律**：`write_user_level` **先 validate 后落盘**——非法档拒写返回 false（绝不留脏档在盘）；合法档序列化为 UTF-8/缩进 2/尾换行契约单 JSON。写入后须重扫才进内存表（本函数只负责原子落盘）。

### 13.4 编辑器五件套 → 契约单 JSON（可选推荐项，已落地）

`LevelLibrary.convert_editor_level(<编辑器 level_N 目录>)`（:465，GDScript 等价实现，逻辑=AB-1 导入脚本 `AI工作记录/批次AB_走查_20260925/ab1_import_editor_levels_temp.py` 与 `test_w_contract` 镜像组装 `_mirror_assemble_doc`）：

### 13.5 遮蔽规则与优先级（拍板）

1. **主进度永不消费用户关**：`get_level(chapter)`（:284）只在内置表 `_levels` 取——内置关与用户关**同 chapter 也不互相遮蔽**（两表独立；主菜单/图鉴/关卡路由零改动）。
2. **合并视图确定性序**：`get_merged_level_list()`（:200）=内置 5 关 + 用户关共存，chapter 升序；**同 chapter 内置排前**（内置优先，稳定序由两表拼接先后天然给出）。
3. **内置关不挤出用户关**：同章用户关仍在用户表与合并视图中（进用户关须显式走 `get_user_level(id)`，不经 `get_level`）。
4. **零自动路由**：本期启动扫描仍是 `scan_directory()`（main.gd:192），玩家放入 `user://user_levels/` 的档**不进游戏任何可见列表**（功能在游戏内不可达 = 拍板的「先不加」 hedging）。
